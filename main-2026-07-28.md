## Рекомендуемая архитектура (Tier 2 — оптимальный баланс)

### 1. Central config — файл настроек по URL

Добавить в приложение механизм **managed config**:

```
При старте:
  1. Загружает https://team-server/mini-ai-config/settings.json
  2. Мержит с локальными настройками (remote — базовые, local — переопределения)
  3. Локальные API-ключи, HWND, пути остаются per-machine
```

Что изменить:
- В `SettingsContext` добавить `remoteConfigUrl` (пустая строка = выключено)
- `load_settings()` на Rust: после чтения локального файла, если указан URL — скачать, распарсить, смержить (глубокий merge, локальные поля перекрывают)
- Чувствительные поля (`api_key`, `proxy.password`, MCP `password`) — НЕ перезаписываются из удалённого конфига

### 2. LLM профили — шаблон + локальные ключи

- `llm_profiles.json` содержит заглушки профилей (provider, model, base_url — без `api_key`)
- Каждый разработчик через Export/Import восстанавливает только свои ключи
- Либо добавить в managed config секцию `llm_profiles` (без ключей), которая смерживается с локальной

### 3. BSL Language Server — удалённый режим

В `settings.bsl_server` уже есть `remote_url`. Настроить:
```
bsl_server: {
  enabled: true,
  remote_url: "ws://dev-server:8025/lsp",
  auto_download: false
}
```

На сервере:
- Установить Java 17+
- Запустить BSL LS: `java -jar bsl-language-server.jar --tcp=8025`

Каждый разработчик подключается к нему, Java не нужна локально.

### 4. Tauri Updater — автоматические обновления

Добавить `tauri-plugin-updater`:
- Настроить `pubkey` + endpoint в `tauri.conf.json`
- Выкладывать релизы на GitHub Releases
- Приложение проверяет обновления при старте и уведомляет

### 5. Развёртывание — MSI через GPO или скрипт

Сейчас собирается MSI и NSIS. Для команды:
- Положить MSI на сетевую шару

```powershell

# Создать settings.json с remoteConfigUrl

  # ... прочие умолчания
}
New-Item -Force "$env:LOCALAPPDATA\MiniAI1C\settings.json" -Value ($config | ConvertTo-Json)
```

- Запускает каждый MCP сервер как stdio-процесс
- Принимает HTTP-запросы от клиентов
- Пересылает JSON-RPC в stdio сервера и обратно

Есть готовые решения:
- `@modelcontextprotocol/inspector` (может проксировать stdio → HTTP)
- Написать простой gateway на Node.js (~100 строк)

## Компоненты

### 1. Сервер (`mini-ai-1c-server`)

**Rust** с фреймворками:
- `axum` — HTTP API + WebSocket
- `tokio` — async runtime
- `rusqlite` / `sqlx` — SQLite
- `tower-http` — CORS, статика
- `rust-embed` — встроить админ-панель в бинарник
- `notify` — file watcher для авто-реиндекса

**Режимы запуска:**
```bash
# Linux
./mini-ai-1c-server --data-dir /data/mini-ai-1c

# Windows
mini-ai-1c-server.exe --data-dir D:\MiniAI1C\Server
```

**Модули:**

| Модуль | Назначение |
|--------|-----------|
| **MCP Gateway** | Принимает HTTP-запросы от клиентов, проксирует JSON-RPC в stdio каждого процесса. Поддерживает пул соединений, авто-рестарт упавших, health checks |
| **Config API** | `GET /api/client/config` — отдаёт клиентскую конфигурацию (MCP серверы, BSL LS URL, skills; `POST /api/admin/config` — управление |
| **Skills Registry** | База знаний для AI-агента: какие MCP инструменты доступны, их схемы, описания, категории |
| **File Watcher** | Следит за изменениями в `/data/1c/configs/`, при изменениях запускает реиндексацию mcp-1c-search |
| **Updater** | Хранит клиентские сборки (ZIP), отдаёт версии клиентам |
| **Admin Dashboard** | Встроенная веб-панель (SPA), скомпилирована в бинарник через `rust-embed` |

### 2. Admin Dashboard

Веб-интерфейс (React, как и основное приложение):
- **Дашборд** — статус сервера, здоровье MCP, последние ошибки
- **MCP Серверы** — список, add/edit/remove, env vars, команды
- **Конфигурации 1С** — управление профилями выгрузок, пути, триггер реиндекса
- **Скиллы** — просмотр, редактирование, включение/отключение инструментов для AI
- **Клиенты** — версии, авто-обновления, загрузка новых сборок
- **Логи** — просмотр логов сервера и MCP-процессов

**Что меняется в существующем `mini-ai-1c`:**

| Изменение | Где |

## Полный анализ архитектуры MCP в Mini AI 1C

### 1. Обзор архитектуры

Архитектура MCP имеет три транспортных типа:

| Transport | Значение | Когда используется |
|-----------|----------|-------------------|
| `Stdio` | Запускается дочерний процесс, JSON-RPC по stdin/stdout | Встроенные серверы, сторонние MCP-серверы Node.js |
| `Http` | JSON-RPC по HTTP с опциональной сессией MCP | Пользовательские серверы, 1C-расширение Kharin |
| `Internal` | Rust-трейт `InternalMcpHandler`, вызывается напрямую | BSL Language Server (bsl-ls) |

### 2. MCP-серверы на TypeScript (папка `mcp-servers/`)

Все три скомпилированы в `.cjs`, встроены в двоичный файл Tauri через `include_bytes!` и автоматически извлекаются при первом запуске.

#### 2.1 `1c-help.ts` (идентификатор: `builtin-1c-help`)

- **Назначение**: Полнотекстовый поиск по справочным файлам 1C:Enterprise (.hbk). Он индексирует официальную документацию платформы в локальную базу данных SQLite с FTS5.
- **Инструменты**: `search_1c_help`, `get_1c_help_topic`, `list_1c_help_versions`, `reindex_1c_help`
- **Транспорт**: Stdio (запускается Node.js)
- **Доступ к локальной файловой системе**: **ДА, критично**
  - Сканирует каталоги установки 1C (`C:\Program Files\1cv8`, `/opt/1cv8`) для поиска установленных версий платформы.
  - Читает бинарные файлы `.hbk` (библиотека `hbk-parser.ts`) -- нативный парсер, который извлекает HTML-страницы из специализированного ZIP-контейнера.
  - Создает базу данных SQLite в `%APPDATA%/com.mini-ai-1c/help/help.db`.
  - Записывает индексные файлы на диск во время индексации (WAL-журналы).
- **Локальные процессы**: Никаких. Только чтение файлов.
- **Может ли работать удаленно**: **НЕТ**. Ему нужен физический доступ к каталогу установки 1C и файлам `.hbk` на локальном диске. Индексация требует чтения ~50 000+ файлов из ZIP-архива, что непрактично удаленно.
- **Канал**: Stdio (через `StdioServerTransport` от SDK MCP)
- **Отчеты о статусе**: Отправляет строки `HELP_STATUS:` через stderr, которые парсятся в `mcp_client.rs`.

#### 2.2 `1c-naparnik.ts` (идентификатор: `builtin-1c-naparnik`)

- **Назначение**: Прокси-сервер к `code.1c.ai` (API ИИ-помощника 1C, "Напарник"). Оборачивает внешнее облачное API в инструменты MCP.
- **Инструменты**: `ask_1c_ai`, `explain_1c_syntax`, `check_1c_code`
- **Транспорт**: Stdio (запускается Node.js)
- **Доступ к локальной файловой системе**: **НЕТ**. Ничего не читает с диска.
- **Зависимости**: `ONEC_AI_TOKEN` -- обязательная переменная окружения (API-токен).
- **API-вызовы**: Все вызовы идут к `https://code.1c.ai/chat_api/v1/`:
  - `POST /conversations` (создать сессию)
  - `POST /conversations/{id}/messages` (отправить сообщение, получить SSE-поток)
  - Взаимодействие с инструментами на стороне сервера: отправляет обратно `"rejected"`, так как этот сервер сам не выполняет инструменты.
  - Использует retry-логику (3 попытки) для 5xx/429 ошибок.
- **Сессии**: Управляет пулом сессий (максимум 10, TTL 1 час) в памяти.
- **Локальные процессы**: Никаких.
- **Может ли работать удаленно**: **ДА**. Это исключительно облачный API-клиент. Он может работать где угодно, где есть доступ в интернет. Фактически, он предпочтителен для удаленного запуска.
- **Канал**: Stdio (SDK MCP) -> HTTP (к code.1c.ai)

#### 2.3 `1c-metadata.ts` (идентификатор: `builtin-1c-metadata`)

- **Назначение**: Тонкий прокси-сервер MCP к HTTP-сервису, работающему внутри 1C:Enterprise. Он ретранслирует стандартные MCP-запросы (список инструментов, вызов инструментов, ресурсы, промпты) через JSON-RPC 2.0 к эндпоинту HTTP 1C.
- **Инструменты**: Динамически получает их из HTTP-API 1C.
- **Транспорт**: Stdio (запускается Node.js)
- **Доступ к локальной файловой системе**: **НЕТ напрямую**. Однако он подключается к `http://localhost/base/hs/mcp` (может быть переопределен через `ONEC_METADATA_URL`).
- **Аутентификация**: Базовая (из `ONEC_USERNAME`/`ONEC_PASSWORD`).
- **Тайм-аут**: 5 секунд на каждом вызове.
- **Локальные процессы**: Подключается к запущенному экземпляру 1C:Enterprise (сеансу Configurator или Enterprise), предоставляющему HTTP-сервис по URL-адресу.
- **Может ли работать удаленно**: **ДА, ЕСЛИ URL-адрес 1C доступен удаленно**. Архитектура "тонкий прокси" означает, что он просто перенаправляет все вызовы на `ONEC_METADATA_URL`. Если 1C-сервис опубликован по сетевому адресу (например, `http://192.168.1.100/mcp`), этот прокси может работать удаленно. В текущей конфигурации по умолчанию используется `http://localhost/base/hs/mcp`, что является локальным.
- **Канал**: Stdio (SDK MCP) -> HTTP (к JSON-RPC 1C)

#### 2.4 Библиотека: `hbk-parser.ts`

- Нативный TypeScript-парсер для бинарного формата `.hbk` 1C.
- Извлекает ZIP-архив `FileStorage` из контейнера HBK и распаковывает HTML-страницы справки.
- Никаких внешних зависимостей (JAR/Java не требуется).

### 3. MCP-мост Rust (`mcp_client.rs`)

#### 3.1 Менеджер сессий (`McpManager`)

- Глобальный синглтон (`lazy_static`), управляющий всеми MCP-сессиями.
- Хранит карту `HashMap<String, (McpServerConfig, Arc<McpSession>)>`.
- Поддерживает регистрацию внутренних обработчиков (`register_internal_handler`).
- Метод `reconfigure()` перезапускает сессии при изменении настроек:
  - Удаляет серверы, которых больше нет в настройках.
  - Обновляет/создает серверы с измененными конфигурациями.
  - Обрабатывает перезапуск BSL Language Server.
  - Слушатель файлов (`start_settings_watcher`) отслеживает изменения `settings.json`.

#### 3.2 Как создаются сессии (`McpSession::new`)

```rust
match config.transport {
    McpTransport::Internal => { /* lookup handler by id */ }
    McpTransport::Http => { McpSession::new_http(config) }
    McpTransport::Stdio => { McpSession::new_stdio(config, debug_mode).await }
}
```

#### 3.3 Stdio (запуск процесса)

- Разрешает путь к команде с помощью нескольких стратегий:
  1. Ресурсы MSI (bundled installer)
  2. Относительно двоичного файла EXE (портативный)
  3. Встроенные байты (извлекаются на диск при первом запуске)
  4. Путь для разработки (`src-tauri/mcp-servers/` или `mcp-servers/`)
- Для Node.js/tsx: заменяет `.ts` на `.cjs`, разрешает Node, обрабатывает `npx` → `npx.cmd`.
- Для .exe: разрешает `mcp-1c-search.exe` через те же стратегии.
- В производстве: если команда является запускатором tsx, переключается на использование напрямую `node` и использования `.cjs` для портативности.
- Создает дочерний процесс с `CREATE_NO_WINDOW` и `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.
- Создает задачу записи (отправляет JSON-RPC через stdin) и задачу чтения (читает stdout, парсит ответы JSON-RPC).
- Строки stderr собираются как логи; специальные префиксы (`HELP_STATUS:`, `SEARCH_STATUS:`) парсятся для состояния сервера.

#### 3.4 HTTP-транспорт

- Поддерживает потоковый HTTP MCP (SSE) и стандартный JSON-RPC по HTTP POST.
- Session management: автоматический initialize handshake (`initialize` → `notifications/initialized`).
- Обнаруживает ответы "session required" и автоматически повторяет попытку с повторной инициализацией.
- Отслеживает `MCP-Session-Id` заголовок для поддержания сессии.
- Health probing: для HTTP-серверов периодически вызывает `list_tools` для проверки состояния (Connected/Offline/Error).

#### 3.5 Внутренний транспорт

- Просто вызывает методы `InternalMcpHandler` напрямую.
- Используется для BSL Language Server.

## 5. How Messages/Chats Are Currently Managed

1. **Session persistence**: `useChatSessions` hook manages `ChatSession[]` stored in `localStorage`. Each session has `id`, `title`, `createdAt`, `updatedAt`, and `messages: ChatMessage[]`.

2. **Active session flow**:
   - `ChatProvider` uses `useChatSessions` to get `sessions`, `activeId`, `activeSession`, and CRUD operations.
   - When `activeId` changes, messages are loaded from `activeSession.messages`.
   - Messages are synced back via `updateSessionMessages` on every `messages` state change.

3. **New message flow**: `sendMessage()` creates a `ChatMessage`, appends it to `messages`, checks if `activeSessionId` exists (creates session if not), then calls `api.streamChat()` backend. Streaming responses update messages via Tauri events (`chat-chunk`, `chat-thinking-chunk`, `tool-call-*`, `chat-done`).

4. **Draft mode**: When `activeId` is `null` (no saved session), messages exist only in React state. Calling `startDraft()` sets `activeId = null`. When a real message is sent, `createSession()` is called to persist.

5. **Session switching**: `switchChat(id)` calls `switchSession(id)` which changes `activeId`, triggering `useEffect` to load that session's messages. The ChatSessionsPopover in the Header provides the UI for this.

6. **Context compression**: Handled in `buildCompressedPayload()` — either `sliding_window` (drops middle messages) or `summarize` (calls `compact_context` API) when token count exceeds 75% of context window.

## 6. How `selectWindow` and `bindingStatus` Work

### `selectWindow(window: WindowInfo)`:
- Constructs a `ConfiguratorWindowBinding` from the selected window via `bindConfiguratorWindow()`
- Persists to settings via `updateSettings`: stores `hwnd`, `pid`, `title`, `config_name`

### `bindingStatus` resolution:
- `resolveConfiguratorBinding()` takes the stored binding and detected windows
- Resolution order: by exact `hwnd` → by `process_id` → by `title` → by `config_name`
- Returns `'resolved'` (hwnd match), `'rebound'` (pid/title/config_name rebound), `'missing'` (no match), `'ambiguous'` (multiple matches), or `'unselected'` (no binding)

### Auto-refresh:
- Windows scanned every 10 seconds via `setInterval`
- Auto-selects single available window when nothing is bound

### In ChatArea:
- `bindingStatus` drives the hint text below the input: shows different messages for each status
- `selectedHwnd` controls whether code-fetch buttons are enabled
- `getCode()` resolves the active window and calls `api.getCodeFromConfigurator(hwnd, useSelectAll)`

### 2. Как EditorBridge общается с конфигуратором

**Архитектура (трехзвенная):**

```
EditorBridge.exe (C#, .NET 8, self-contained)
       ↕  Named Pipe \\.\pipe\mini-ai-editor-bridge-<USERNAME>
editor_bridge.rs (Rust, этот модуль)
       ↕  вызовы функций
commands/configurator.rs (Tauri команды)
       ↕  invoke()
React Frontend (TypeScript)
```

**Детали:**

- **Транспорт:** Windows Named Pipe (`\\.\pipe\mini-ai-editor-bridge-<USERNAME>`).
  - Имя пайпа можно переопределить через переменную окружения `MINI_AI_EDITOR_BRIDGE_PIPE`.
- **Протокол:** JSON-RPC по строкам (каждая строка — один запрос/ответ).
  - Формат запроса: `{"command": "get_editor_context", "args": {"hwnd": 123456, ...}}`
  - Формат ответа: `{"ok": true, "result": {...}}` или `{"ok": false, "error": "...", "message": "..."}`
- **EditorBridge.exe** получает доступ к редактору 1С через **UIAutomation TextPattern**. Он не использует буфер обмена и не крадет фокус.
- **Запуск:**
  1. По умолчанию — на `winsta0\default` (отдельный desktop) через `CreateProcessW` с `CREATE_NO_WINDOW` (чтобы не зависеть от сессии пользователя в RDP).
  2. Альтернативно — как обычный child process с `CREATE_NO_WINDOW`.
  3. Режим можно принудительно задать через `MINI_AI_EDITOR_BRIDGE_LAUNCH=child`.
- **Watchdog:** Фоновый тред проверяет каждые 2 секунды, жив ли EditorBridge. Если нет — перезапускает.
- **Поиск exe:** По пути из настроек → рядом с app binary → `target/debug/editor-bridge/` → `tauri-app/src-tauri/editor-bridge/`.
- **Загрузка:** EditorBridge.exe скачивается с GitHub (релизы `hawkxtreme/1ConfBridge`) через `download_editor_bridge()`.

### 3. Механизм определения активной конфигурации

Процесс **трехуровневый**: поиск окон → привязка → парсинг заголовка.

#### Шаг 1: Поиск окон конфигуратора (Rust, `configurator.rs`)

Функция `find_configurator_windows(pattern: &str)`:

1. Вызывает `EnumWindows()` для перебора всех окон верхнего уровня.
2. Для каждого видимого окна проверяет:
   - **Процесс:** `K32GetModuleFileNameExW` — имя exe должно оканчиваться на `1cv8.exe`, `1cv8c.exe`, `1cv8s.exe`, `1cv8t.exe`, `1cv8ct.exe` или `1cv8st.exe`.
     - В **RDP-режиме** фильтр по процессу отключается, т.к. `OpenProcess` не работает через RDP.
   - **Заголовок:** содержит одну из частей паттерна (через `|`): по умолчанию `"Конфигуратор|1C:Enterprise"`.
3. Возвращает `Vec<WindowInfo>` с полями: `hwnd`, `title`, `process_id`.

#### Шаг 2: Привязка к выбранному окну (TypeScript, `configuratorBinding.ts`)

Функция `resolveConfiguratorBinding(binding, windows)`:

Ищет окно в порядке приоритета:
1. **По HWND** (точное совпадение) — если окно все еще существует.
2. **По PID** — если процесс жив и у него только одно окно.
3. **По заголовку** — точное совпадение нормализованного заголовка.
4. **По имени конфигурации** — извлеченному из заголовка.

Статусы привязки: `'resolved'` | `'rebound'` | `'missing'` | `'ambiguous'` | `'unselected'`.

Данные привязки хранятся в `settings.configurator`:
- `selected_window_hwnd: Option<isize>`
- `selected_window_pid: Option<u32>`
- `selected_window_title: Option<String>`
- `selected_config_name: Option<String>`

Эти поля считаются runtime-only — очищаются при экспорте/импорте настроек (`clear_runtime_only_settings`).

#### Шаг 3: Парсинг заголовка окна (TypeScript, `configurator.ts`)

Функция `parseConfiguratorTitleFull(title)` парсит формат:

```
{ObjectType} {ObjectName}: {ModuleType} [{flags}] - Конфигуратор - {ConfigName}
{FilePath}: {ModuleType} - Конфигуратор - {ConfigName}
Конфигуратор - {ConfigName}
```

Извлекает:
- `config_name` (имя конфигурации/базы)
- `object_type` (Документ, Справочник, ОбщийМодуль и т.д.)
- `object_name` (имя объекта)
- `module_type` (МодульОбъекта, МодульФормы и т.д.)
- `execution_context` (managed_form | server | common_module | client | unknown)
- `read_only` (флаг только для чтения)
- `is_external_file` (внешняя обработка/отчет)

#### Шаг 4: Автоматическое обновление (TypeScript, `ConfiguratorContext.tsx`)

- **Периодический опрос:** каждые 30 секунд вызывается `refreshWindows()` — повторяет поиск окон и перепривязку.
- **Автовыбор:** если окно не выбрано, а найдено ровно одно — оно привязывается автоматически.
- **Авто-переключение профиля поиска MCP:** при смене имени активной конфигурации автоматически переключается search-профиль на MCP-сервере `builtin-1c-search`.

**Полная привязка использует четыре идентификатора:**

| Идентификатор | Тип | Как получается | Где хранится |

**Фильтрация окон (только 1С):**

- `1cv8.exe` (толстый клиент/конфигуратор)

- `1cv8s.exe` (толстый клиент)

**Mouse Hook (Ctrl+ПКМ):**

`mouse_hook.rs` устанавливает `WH_MOUSE_LL`. При нажатии Ctrl+ПКМ:
1. Проверяет, что окно под курсором принадлежит процессу 1С (`is_configurator_window`).
2. Подавляет WM_RBUTTONDOWN и WM_RBUTTONUP (не дает открыться контекстному меню 1С).
3. Сохраняет событие и после отпускания мыши эмитирует Tauri-событие `configurator-rclick`.
4. Фронтенд открывает overlay с быстрыми действиями.
5. **EditorBridge enabled** определяет, перехватывать ли Ctrl+ПКМ вообще.

The entire MCP lifecycle is managed in **`E:\1C_AI\mini-ai-1c\tauri-app\src-tauri\src\mcp_client.rs`** (~2307 lines).

### Three transport types (defined in `settings.rs`):

### Spawning logic (for Stdio transport — the most common):

1. **`McpManager::get_client()`** — entry point. Returns a cached `Arc<McpSession>` or creates a new one.
2. **`McpSession::new_stdio()`** (starts at line 1101):
   - Reads `command` and `args` from config
   - **Path resolution cascade** for Node.js `.cjs` files (lines 1113-1215): Tries 5 strategies in order:

     3. **Embedded portable** (`include_bytes!` → extract to disk) — release builds only, extracts on first run
     4. **Dev mode path** (`src-tauri/mcp-servers/1c-naparnik.cjs`) — during development
     5. **Dev mode fallback** (`mcp-servers/1c-naparnik.cjs`) — if cwd is already `src-tauri/`
   - Same cascade for `.exe` binaries (lines 1218-1295)
   - In **production** (non-debug), Node.js launchers (`npx`, `tsx`) are replaced with plain `node` for portability (lines 1312-1339)
   - On Windows, `npx`/`npm` commands get `.cmd` appended (line 1304)
   - Creates a `tokio::process::Command` with:
     - `stdin`/`stdout`/`stderr` piped
     - `.kill_on_drop(true)`

     - Assigned to a Windows Job Object for cleanup on crash (line 1374)
3. **Stdio JSON-RPC communication**:

   - Reader task: parses JSON-RPC responses from stdout

/**
 * Ищет установленные версии платформы 1С.
 * Если задан ONEC_HELP_PATH — использует его как единственный путь поиска.
 * Иначе — стандартные пути установки 1С:Предприятие.
 * Возвращает последнюю по семантической версии.
 */
function findPlatform(): PlatformInfo | null {
    const customPath = process.env.ONEC_HELP_PATH?.trim();

    const { platform } = process;

    const searchPaths = customPath
        ? [customPath]
        : platform === 'win32'
            ? [
                'C:\\Program Files\\1cv8',
                'C:\\Program Files (x86)\\1cv8',
            ]
            : [
                '/opt/1cv8',
                '/opt/1cv8/x86_64',
                '/usr/share/1cv8',
            ];

    if (customPath) {
        log(`Используется пользовательский путь к платформе: ${customPath}`);
    }

    const platforms: PlatformInfo[] = [];

    for (const basePath of searchPaths) {
        if (!existsSync(basePath)) continue;

        let entries: string[] = [];
        try {
            entries = readdirSync(basePath);
        } catch {
            continue;
        }

        for (const entry of entries) {
            // Версия платформы — папка типа "8.3.27.1989"
            if (!/^\d+\.\d+\.\d+\.\d+$/.test(entry)) continue;

            const binPath = join(basePath, entry, 'bin');
            if (!existsSync(binPath)) continue;

            // Проверяем наличие нужного .hbk файла
            const hbkPath = join(binPath, 'shcntx_ru.hbk');
            if (!existsSync(hbkPath)) continue;

            platforms.push({ version: entry, binPath });
        }
    }

    if (platforms.length === 0) return null;

    // Сортируем по семантической версии — берём последнюю
    platforms.sort((a, b) => {
        const partsA = a.version.split('.').map(Number);
        const partsB = b.version.split('.').map(Number);
        for (let i = 0; i < 4; i++) {
            if ((partsA[i] || 0) !== (partsB[i] || 0)) {
                return (partsB[i] || 0) - (partsA[i] || 0);
            }
        }
        return 0;
    });

    return platforms[0];
}

#### How JSON-RPC messages are read/written over stdin/stdout

```rust
// stdin/stdout are wrapped in tokio async I/O
let stdin = tokio::io::stdin();
let stdout = tokio::io::stdout();
let stdout = Arc::new(tokio::sync::Mutex::new(stdout));  // shared for concurrent writes

let mut reader = BufReader::new(stdin);
let mut line = String::new();

loop {
    line.clear();
    match reader.read_line(&mut line).await {
        Ok(0) => break,                // EOF = client disconnected
        Ok(_) => {
            let trimmed = line.trim();
            if trimmed.is_empty() { continue; }

            // Parse incoming JSON-RPC request
            let request: Value = serde_json::from_str(trimmed)?;

            // Notifications (no "id") are silently dropped
            let id = request.get("id")?;

            let method = request["method"].as_str().unwrap_or("");
            let params = request.get("params").cloned().unwrap_or(json!({}));

            // Spawn each request as an independent async task
            tokio::spawn(async move {
                let result = handle_method(&method, &params, &workspace).await;
                let response = match result {
                    Ok(res) => json!({
                        "jsonrpc": "2.0",
                        "id": id,
                        "result": res
                    }),
                    Err(msg) => json!({
                        "jsonrpc": "2.0",
                        "id": id,
                        "error": { "code": -32603, "message": msg }
                    }),
                };
                let resp_str = serde_json::to_string(&response).unwrap_or_default();
                let mut out = stdout_task.lock().await;
                let _ = out.write_all(resp_str.as_bytes()).await;
                let _ = out.write_all(b"\n").await;   // newline-delimited JSON
                let _ = out.flush().await;
            });
        }
        Err(_) => break,
    }
}
```

**Key patterns:**
1. **One JSON object per line** on stdin/stdout (newline-delimited JSON).
2. Each line is parsed as `serde_json::Value` (no manual structs for the protocol).
3. Requests without an `"id"` field are treated as notifications and ignored (per JSON-RPC 2.0 spec).
4. Each request is **spawned as an independent `tokio::spawn`** task so heavy tools don't block others.
5. stdout is wrapped in `Arc<Mutex<>>` for safe concurrent writes from multiple tasks.
6. Responses use the standard JSON-RPC 2.0 envelope: `{"jsonrpc":"2.0","id":...,"result":...}` or `{"jsonrpc":"2.0","id":...,"error":{"code":...,"message":...}}`.

## 2. Exact JSON format for a stdio MCP server in `settings.json`

The file is located at `%LOCALAPPDATA%\MiniAI1C\settings.json`. Here is the exact format for a stdio-based external MCP server:

```json
{
  "mcp_servers": [
    {
      "id": "my-external-server",
      "name": "My External MCP Server",
      "enabled": true,
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "some-mcp-server-package"],
      "env": {
        "MY_VAR": "some-value",
        "ANOTHER_VAR": "value2"
      },
      "url": null,
      "login": null,
      "password": null,
      "headers": null
    }
  ]
}
```

For HTTP-based servers:

```json
{
  "id": "my-http-server",
  "name": "My HTTP MCP Server",
  "enabled": true,
  "transport": "http",
  "url": "http://myserver:8080/mcp",
  "login": "user",
  "password": "secret",
  "headers": {
    "X-Custom": "value"
  },
  "command": null,
  "args": null,
  "env": null
}
```

**Key points about the JSON:**
- All `Option` fields serialize as `null` when `None`, but serde also accepts missing keys altogether.
- The `transport` field uses lowercase: `"stdio"`, `"http"`, or `"internal"`.
- For stdio: only `command`, `args`, and `env` are relevant; set `url`, `login`, `password`, `headers` to `null` (or omit them).
- For http: only `url`, `login`, `password`, `headers` are relevant; set `command`, `args`, `env` to `null` (or omit them).
- The `id` must be unique among all servers; built-in IDs are `"builtin-1c-naparnik"`, `"builtin-1c-metadata"`, `"builtin-1c-help"`, `"builtin-1c-search"`, and `"bsl-ls"`.

### 4. Communication Protocol

All MCP servers use **JSON-RPC 2.0 over stdio** (the standard MCP transport), except HTTP servers.

#### Stdio Transport (the primary pattern)
1. The Tauri backend spawns a child process with `stdin`/`stdout`/`stderr` piped.
2. The parent sends JSON-RPC requests as newline-delimited JSON on the child's **stdin**.
3. The child responds with JSON-RPC responses on its **stdout**.
4. The child reports status/progress on **stderr** (parsed by the parent):
   - `1c-help` emits `HELP_STATUS:<state>:<details>` lines
   - `mcp-1c-search` emits `SEARCH_STATUS:<state>:...` and `SEARCH_STATUS_JSON:{...}` lines
5. The parent writes JSON lines to stdin; the child reads via `BufReader::read_line`.
6. Each request is assigned an incrementing `id` for correlation; responses are matched via a `HashMap<id, oneshot::Sender>`.

Example request/response flow:
```
→ {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05",...}}
← {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2024-11-05","capabilities":{"tools":{}},...}}
→ {"jsonrpc":"2.0","method":"notifications/initialized","params":{}}
→ {"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}
← {"jsonrpc":"2.0","id":2,"result":{"tools":[...]}}
→ {"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"find_symbol","arguments":{...}}}
← {"jsonrpc":"2.0","id":3,"result":{...}}
```

#### HTTP Transport (for third-party servers)
- The Rust backend makes HTTP POST requests to the configured URL.
- Supports JSON-RPC over HTTP, SSE streaming (`text/event-stream`), and `Mcp-Session-Id` header for session management (Streamable HTTP).
- Automatically performs `initialize` handshake and retries if server responds with `"session missing"`.
- Health probing runs periodically in the background.

#### Internal Transport (for bsl-ls)
- Direct trait method invocation (`InternalMcpHandler::list_tools()` / `InternalMcpHandler::call_tool()`).
- No serialization overhead.

#### How the app manages MCP server lifecycle:

1. **On startup** (`lib.rs:setup()`):

   - The `bsl-ls` internal handler is registered.
   - The BSL Java Language Server is started and connected.

   - `call_mcp_tool()` looks up a server by ID, creates/reuses a session, calls `tools/call`.
   - `get_mcp_server_statuses()` returns live status (connected/stopped/error) plus index progress for help/search servers.

3. **On settings change** (via file watcher):
   - `McpManager::reconfigure()` diffs old vs new configs.
   - Removes servers no longer present.
   - Restarts servers whose config changed or process died.
   - Reuses sessions where config is unchanged and process is alive.

4. **Resource resolution** (for spawned child processes):
   - The backend tries multiple locations in order:
     1. Tauri resource path (`app_handle.path().resolve(..., BaseDirectory::Resource)`) — for MSI-installed builds.
     2. EXE-relative path (`exe_dir/mcp-servers/<file>`) — for portable/dev builds.
     3. Embedded fallback (`include_bytes!`, extracted to `exe_dir/mcp-servers/` on first launch) — for single-file portable.
     4. Dev-relative paths (`src-tauri/mcp-servers/` or `mcp-servers/`) — for development.

5. **Windows Job Object**: Child processes are assigned to a Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` to ensure they are killed when the parent exits, even on crash.

### 6. Key Patterns Used

| Pattern | Where | Description |
|---|---|---|
| **Stdio JSON-RPC** | All 4 servers + `McpSession` | Standard MCP transport: newline-delimited JSON on stdin/stdout, status on stderr |
| **Lazy-static singleton** | `McpManager` | Global manager holding all active sessions, initialized once |
| **Session reuse** | `McpManager::get_client()` | Reuses McpSession if config unchanged and process alive |
| **Hot-reload** | `McpManager::reconfigure()` | File watcher triggers reconfiguration when settings.json changes |
| **Multiplexed request/response** | `McpSession` - `pending_requests: HashMap<id, oneshot::Sender>` | Each request sends its ID, async response matched via oneshot channel |
| **Background indexing** | `1c-help.ts` `runIndexing()`, `mcp-1c-search/src/main.rs` spawn_blocking | Heavy indexing runs asynchronously so the MCP event loop stays responsive |
| **Stderr status protocol** | `HELP_STATUS:*`, `SEARCH_STATUS:*`, `SEARCH_STATUS_JSON:*` | Servers report progress/ready/unavailable via stderr — parsed by the parent |
| **Transport polymorphism** | `McpSession` enum `TransportImpl` | Three transport implementations (Stdio, Http, Internal) behind a unified API |
| **Embedded resources** | `include_bytes!` for `mcp-servers/*` | Release builds embed all MCP server executables in the main binary |
| **Path resolution chain** | `McpSession::new_stdio()` | Cascading resource lookup: Tauri resource → EXE-relative → embedded → dev-relative |
| **McpClient wrapper** | `McpClient` struct | Convenience wrapper adding timeouts and help-state queries over `McpSession` |
| **Tool cache** | `commands/mcp.rs` - `MCP_TOOLS_CACHE` | `list_mcp_tools()` caches aggregated tool lists for 300s with cache-key invalidation |
