# Анализ: агент выдал неверные документы МЭДОС ООО за сентябрь

## Запрос

Пользователь (Жеребятьев В.В., база `ca2_update_zhvv`, prod) в 03:32–04:52 28.10.2026
спросил «покажи продажи за сентябрь по МЭДОС ООО». Агент выдал чужие/несуществующие
в базе документы (Хп0К-002695, 002707, 002716–002722, «возврат» Хп0К-002729 на
11 147,14 руб.). Пользователь показал реальный список (11 документов), и агент
признал ошибку, но сам причину назвать не смог («история вызовов мне не видна»).

Вопрос: в чём именно ошибся агент, какие запросы делал.

## Диагноз

**Ошибок две, разного рода:**

### 1. Верный ответ «с сентября» был, но в него подмешана галлюцинация про август

Реальные данные за сентябрь (Хп0К-002747, 163 473) агент получил честно
(запросы r22–r24). Но фраза «в августе у МЭДОС было 8 накладных на ~627 тыс.»
не выведена ни из одного результата — это домысел. В следующих двух ответах
(`tools=[]`, без единого запроса) модель «развила» этот домысел в конкретные номера,
даты и суммы (002695…002722, возврат 11 147,14). Все эти цифры — галлюцинация.

Почему модель не перепроверила: история диалога, уходящая в промпт
(`_history_to_messages`, `chat.py:559`), содержит **только user/assistant-тексты** —
результаты инструментов туда не попадают (`pairs = [(m.role, m.content) ... if m.role in ("user","assistant")]`).
Модель видит свой же ответ «8 накладных на 627 тыс.» как факт и опирается на него.
При этом в её собственном финальном сообщении она пишет «история вызовов мне не видна» —
это правда про tool-результаты, но ложное чувство защищённости: ответ-галлюцинация
виден и воспринимается как источник данных.

### 2. Механика, которая довела до этого (вклад бэкенда)

- **Пустой результат `{"rows": []}` не считается ни ошибкой, ни «пустым ответом»**:
  `_is_empty_result` (`loop.py:638`) ищет маркеры «не найдено / 0 записей», а JSON с
  пустым массивом их не содержит. Предохранитель `max_repeat_calls` (stop после 3
  повторов) тоже не сработал — аргументы у r7/r8/r12/r13 различались. Модель получила
  4 «пустых» результата подряд и, вместо остановки, начала перебирать фильтры
  (Партнер/Контрагент/ИНН), потратив ~10 из 26 раундов.
- **Модельная слабость на длинной петле**: 26 раундов, context budget 60k — к финалу
  модель «потеряла нить» и достроила ответ по памяти/догадке (классический дрейф
  локальной модели Qwen3.8-27B на длинных tool-loop'ах).

## План исправления

Ничего не правим — только план. По убыванию эффекта:

### A. Предотвратить «ответ без запросов» (главный фикс)
Файл: `agent/backend/src/app/agent/loop.py` (`run_agent`, ветка `if not resp.tool_calls`).
- Если ответ финальный, а в **этом** вызове `run_agent` ни один инструмент не был
  выполнен (`called == []`) И в истории есть предыдущий ответ по тому же вопросу —
  не возвращать ответ как есть, а сделать один доп. проход с system-подсказкой:
  «Для ответа на вопрос о данных 1С сначала выполни запрос инструментом; если данные
  уже получены ранее — процитируй их, не выдумывай номера/суммы».
  Лёгкий вариант (без доп. LLM-вызова): в промпт агента (`agents/assistant/AGENT.md`,
  прод-контент) добавить жёсткое правило: «Никогда не приводить номера документов,
  даты и суммы, которых нет в результатах инструментов текущего или предыдущих
  запросов. Если данных нет — так и сказать».

### B. Пустой результат `execute_select` — как «пустой ответ»
Файл: `agent/backend/src/app/agent/loop.py`, `_is_empty_result`.
- Добавить маркер для JSON: `'"rows": []'` (и `"rows":[ ]`). Тогда 3 подряд пустых
  выборки по одному инструменту остановят петлю честным сообщением «по этому фильтру
  записей нет», а не перебором фильтров. Риск: модель может легитимно уточнять фильтр
  после пустого результата — поэтому стоп только при `consec_empty >= max_repeat_calls`
  (текущий порог 3) и с текстом, предлагающим уточнить условие.

### C. Сократить длину петли для «покажи данные»-запросов
Файл: `agent/backend/agents/assistant/AGENT.md` (prod) + `patterns/query-patterns.md`.
- Правило: «Не более 10 вызовов execute_select на вопрос; если после 3 разных фильтров
  результат пуст — остановиться и спросить пользователя, а не перебирать дальше».
- В `query-patterns.md` уже есть правило «сравнение ссылок — только через примитивные
  реквизиты», но агент всё равно пробовал `ГДЕ Контрагент = "МЭДОС ООО"` (строка в
  ссылочное поле). Добавить явный пример: фильтр по контрагенту — **по ИНН или Коду**,
  найденным отдельным запросом к Справочник.Контрагенты, и только один вариант фильтра
  на попытку.

### D. Визуализация в UI (обвязка)
Файл: клиент чата 1С / админка (`GET /sessions/{id}/rounds` уже пишет все шаги).
- В пузыре ответа показывать бейдж «N запросов к базе» (из `done.rounds`/`tool_calls`).
  Ответ с `tools=[]` на вопрос о данных — жёлтый маркер «без обращения к базе».
  Это даст пользователю сигнал недоверия до того, как он сверит номера вручную.

### E. Опционально: tool-результаты в истории
Файл: `agent/backend/src/app/api/chat.py` (`_history_to_messages`) + миграция.
- Сохранять в `messages` (отдельное поле или role="tool") компактные результаты
  инструментов и включать их в промпт сжато (по 1–2 строкам на запрос: «запрос X → N строк,
  ключевые значения»). Дорого по контексту; делать только если A+B+C не закрывают проблему.

### Проверка после фикса
1. Replay сценария: вопрос «продажи за сентябрь по МЭДОС ООО» на `ca2_update_zhvv` —
   ответ должен содержать ровно те документы, что вернул execute_select (сверка по логам).
2. Намеренно пустой фильтр (несуществующий контрагент) × 3 — петля должна остановиться
   с честным сообщением, а не додумать данные.
3. `uv run pytest` + smoke (`scripts/smoke_tools.py --replay`).

## Дополнение: почему агент не использовал паттерн 1c-queries

Вопрос пользователя: в `patterns/1c-queries.md` много правил и примеров — почему агент их не применил?

### Факты из логов (28.10, обе попытки)

| Попытка | get_pattern | Что загрузил |
|---|---|---|
| 03:32 (r1) | да | `get_pattern({"name":"1c-queries"})` — весь файл (448 строк) в контекст |
| 03:47 (r1) | да | `get_pattern({"name":"query-patterns"})` — компактный (46 строк) + `search_knowledge_base` |

То есть паттерн агент **читал в обеих попытках**. Но применил из него только самое
видимое (`ВЫБРАТЬ РАЗРЕШЕННЫЕ`, `ДАТАВРЕМЯ`) и проигнорировал ключевые правила:

- **1c-queries.md, правило 3** — «Сравнение ссылочных полей — только через
  примитивные реквизиты» (`ГДЕ Документ.Контрагент = Справочник.Контрагенты.Ссылка`
  помечено ❌). Агент в r7/r8 написал ровно это: `ГДЕ Контрагент = "МЭДОС ООО"` → пусто.
- **1c-queries.md, «Типичные ошибки»** — «Ошибка при сравнении ссылок … сравнивать
  через .Код/.Наименование/.ИНН» — тоже проигнорировано (хотя в r20–r23 агент сам
  дошёл до `Контрагент.ИНН` — но только после 4 пустых результатов).
- **query-patterns.md, правило 7** — «первое точное совпадение по name из
  `get_counterparty` — это он, дальше работай со ссылкой». Агент **не мог** это сделать:
  `get_counterparty` (и `run_skd_report`, `get_stock_balance`) отсутствуют в списке
  `tools:` агента assistant (`agents/assistant/AGENT.md`, prod) — там только
  execute_select/execute_query/validate_query + метаданные + search-*.
- **query-patterns.md, правило 5** — «Один запрос чинить максимум 2 раза. Третья ошибка
  подряд — остановиться и спросить». В попытке 1 было 3 ошибки подряд → сработал
  бэкендский circuit breaker (он сильнее правила), но в попытке 2 модель получила
  4 пустых результата подряд и продолжала перебирать фильтры до 26-го раунда.

### Почему «прочитал — не применил»

1. **Ленивая подгрузка + конкуренция за внимание.** `get_pattern` грузит текст в
   контекст как tool-результат (не system). В попытке 2 рядом были ещё
   `search_knowledge_base`, `get_metadata_tree` (огромный JSON на ~20 000 символов —
   съедает заметную часть окна) и `get_metadata_structure`. Правила из паттерна
   конкурируют за внимание с десятками других фрагментов; к 15–26 раунду они уже
   «под завалом» свежих tool-результатов. Слабая модель (Qwen3.8-27B, thinking off)
   на длинной петле теряет старые инструкции — это и есть дрейф, описанный выше.
2. **Правило 3 паттерна формально соблюдено — но по «худшему» варианту.**
   Правило 3 (`1c-queries.md`) запрещает прямое сравнение ссылок и даёт два допустимых
   стиля: `Контрагент.Наименование = "..."` ИЛИ `Контрагент.Код = "..."`. Агент в r7/r8
   написал `ГДЕ Контрагент = "МЭДОС ООО"` — т.е. **не** `.Наименование`, а голый
   ссылочный реквизит, сравненный со строкой. Это не то, что разрешает правило 3:
   модель «опустила» подполе `.Наименование` (в описании тулзы execute_select есть
   пример именно с `Партнер.Наименование ПОДОБНО`, т.е. сигнал был). Результат —
   пустая выборка **без ошибки** (строка в ссылочном поле не совпадает ни с чем),
   и модель приняла «пусто» за «данных нет», вместо того чтобы догадаться, что фильтр
   построен некорректно. Правильный для execute_select стиль — через примитивные
   подполя: `Контрагент.ИНН = "..."` / `.Код` / `.Наименование`.
3. **Правильный инструмент для этого сценария вырезан из агента.** `get_counterparty`
   как раз решает задачу «найти контрагента и дать ссылку/ИНН одним вызовом» (правило 7
   паттерна). В tools: assistant его нет — агент обречён искать руками execute_select.
   **Решение пользователя (28.10):** `get_counterparty`, `run_skd_report`,
   `get_stock_balance` намеренно не актуальны и возвращать их в агента НЕ надо —
   сценарий закрывается через execute_select + фильтр по примитивным подполям
   (.ИНН/.Код/.Наименование). Тогда пункт F плана сводится к правке паттерна/промпта
   (см. G, H), а не к возвращению тулз.

### Что это меняет в плане исправления

Дополнение к пунктам A–C предыдущего плана. Решение пользователя: курируемые тулзы
`get_counterparty`/`run_skd_report`/`get_stock_balance` НЕ возвращаются в агента —
они пока не актуальны; сценарий «продажи по контрагенту» закрывается через
execute_select + фильтр по примитивным подполям. Значит:

- **F (пересмотрен).** Правка паттерна `query-patterns.md`: правило 7 про
  `get_counterparty` заменить на работающий алгоритм без этой тулзы —
  «1) один запрос к Справочник.Контрагенты с ПОДОБНО по наименованию → взять точное
  совпадение; 2) дальше фильтр в документе только через примитивные подполя ссылки:
  `Контрагент.ИНН = "..."` (или `.Код`); прямое `ГДЕ Контрагент = "строка"` ЗАПРЕЩЕНО
  — строка в ссылочном поле даёт пустой результат без ошибки».
- **G.** В правиле 3 паттерна `1c-queries.md` добавить явный запрет и пример:
  «ЗАПРЕЩЕНО сравнивать голый ссылочный реквизит со строкой:
  `ГДЕ Контрагент = "ООО Ромашка"` — строка в ссылочном поле не совпадает ни с чем,
  результат пустой без ошибки. Всегда указывай подполе: `.Наименование`, `.Код`, `.ИНН`».
  Это закрывает разрыв, который модель закрыла ошибочно (опустила `.Наименование`).
- **H.** Короткий критический блок паттерна (правила 3, 5 + новый F + «пустой результат ≠
  данных нет, но 3 пустых подряд — остановиться») продублировать в AGENT.md assistant
  как system-инструкцию: system читается моделью надёжнее tool-результата.
