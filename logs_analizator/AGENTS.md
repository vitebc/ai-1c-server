# logs_analizator — анализ логов и планы исправления

Специализированная сессия: **анализ логов** dev/prod сервера ai-1c-server.

## Правила сессии

- **Ничего не правим в проекте.** Только чтение: логи, код (через codegraph), конфигурация.
- Результаты анализа и планы исправления сохраняем **только в эту папку**.
- Быстрый поиск по коду — через `codegraph_codegraph_explore` (не grep/Read по циклу).

## Где лежат логи

### Dev (порт 9225)
- systemd: `journalctl --user -u ai-1c-server-dev.service -f` / `--since "10 min ago"`
- Файл: `<repo>/server.log` (если запущен через `scripts/start-dev.sh`)

### Prod (порт 9224)
- systemd: `journalctl --user -u ai-1c-server-prod.service -f`
- Файл: `/home/test/.config/ai-1c-server/adminka/server.log`
- PID: `/home/test/.config/ai-1c-server/adminka/server.pid`

### Agent backend (Python, prod :8000 / dev :8001)
- systemd: `systemctl --user status ai-1c-agent-*` (если есть)
- Логи docker compose — в `agent/` (см. `agent/AGENTS.md`, `agent/DEV_PROD.md`)

### MCP-серверы (stdio subprocess, поднятые шлюзом)
- Их stdout/stderr уходит в кольцевой буфер Rust-процесса → виден в server.log / journalctl
- Так же доступен через API: `GET /api/logs` (нужен логин)

## Как писать отчёты

Файл: `logs_analizator/<YYYY-MM-DD>_<короткий-тег>.md`

Структура:
1. **Запрос** — что пользователь попросил разобраться, какие временные рамки, dev/prod.
2. **Источники** — какие логи/команды использованы (с точными командами для воспроизведения).
3. **Находки** — хронология событий, выдержки логов (не более ~30 строк на выдержку),
   корреляция с кодом (файл:строка через codegraph).
4. **Диагноз** — корневая причина, если установлена; иначе гипотезы по убыванию вероятности.
5. **План исправления** — шаги, файлы/функции для правки, риски, как проверить после фикса.
   **Не выполнять** — только описать.

## Конвенции

- Язык отчётов: русский.
- Тег в имени файла: латиницей, kebab-case (`2026-10-28_mcp-timeout.md`).
- Если анализ дополняет предыдущий — не создавать новый файл, дописывать в существующий.
